# T-043c0b3a — canonical replay admission core

S69 · 2026-10-31 · D-245. **Pure preparation only: not used by live remotes yet.**

- `Shared.CastAdmission` owns a `CastLedger`, server-only epoch and non-reentrant dispatch. Give each connection a never-reused server scope (e.g. GUID, <=40 alphanumeric/underscore/hyphen bytes); generation is scope:epoch and accepted cast ID is generation:seq. Do NOT rebuild with the same scope at respawn.
- `canonical` validates/copies/freezes finite XYZ, optional point (including Y), bounded move/generation strings and u16 seq. The fingerprint is length-prefixed move ID + binary f64 aim + explicit point marker/XYZ. Generation/seq are the separate ledger key. Signed zero canonicalizes to zero. No decimal rounding or hash collisions; fingerprint <=114 bytes. Compute AFTER wire decoding; Blink vector precision is not restored by f64 encoding.
- `dispatch(state, raw, monotonicNow, authorize)` invokes authorization only for a fresh reservation. The callback receives immutable request and server-derived cast ID. Accepted/failed dispositions are cached; duplicates never call it again, changed payload is refused, expiry/eviction does not clear the sequence watermark. Unknown moves are ordinary callback rejections, not trusted by this module.
- Authorization MUST validate/pay/capture receipt synchronously and not throw. A coroutine guard closes yielded callbacks and caches `internal_error` for yields/errors/bad return contracts, preventing replay of partial work. It does **not** undo already-paid Qi or engine effects; report internal errors and never intentionally use exceptions as rejection. No task.spawn/defer or asynchronous side effects inside authorization. No nested rotate/destroy/dispatch.
- Config.CastProtocol: capacity128, maxAdvance1024, responseSeconds10, renewDistance30000. At the existing 10/s + burst10 remote allowance, this bounds ~10s of legitimate duplicate receipts with headroom. Not a measured network tuning result. Max forward advance leaves room to rotate before half-ring32768. Caller supplies finite monotonic time, pruning on heartbeat/leave.
- `rotate` is only server-driven at character change or `result.renew`; it returns a new epoch, rejects ALL old-generation traffic and drops only cached dispositions, not accepted gameplay/world-hazard state. Never rotate from an arbitrary client generation request. uint32 epoch exhaustion requires a new never-reused scope. b3b must document in-flight rejection/re-sync and keep input predictions gated until matching character generation is available.
- `destroy` clears entries and permanently refuses work. Full accepted schedules/centre/terminal/contact receipts are a DIFFERENT bounded owner in b3c; this core stores only disposition/castId. b4 owns cleanup/adoption. This step does not solve the Z/X timing readiness probes.

Evidence: 10 new pure cases include binary precision/signed-zero/NaN-Y, real CastTransaction duplicate payment, cached failure, bounded 1,000-request eviction, expiry, rollover, rotation/stale identity, renewal threshold, invalid clocks, nested entry, yield/error handling and teardown. CHECK PASS: 327 pure + 7 input + 6 dispatcher mocks + timing + 3 authoring. No actual network, cloud, renderer or publication test.
